# Установка на TrueNAS

Эта инструкция предназначена для TrueNAS с Docker Apps, начиная с SCALE 24.10. Она использует **Custom App → Install via YAML**. В старых выпусках SCALE с Kubernetes такая конфигурация не работает. Точные названия экранов могут различаться по версии; проверьте установленный выпуск перед началом. [Официальная справка TrueNAS 24.10](https://www.truenas.com/docs/scale/24.10/scaleuireference/apps/).

`192.168.1.10` в этой инструкции — пример: замените его на адрес своего NAS. Панель открывается на порту `31800`. Пути к dataset намеренно оставлены как `/mnt/CHANGE_ME/...`: имя пула, существующие dataset и их права нужно выбрать на вашем сервере.

## 1. Подготовить хранилище

До установки выберите pool для Apps в интерфейсе TrueNAS, если он ещё не выбран. Подготовьте два существующих пути:

| Назначение | Путь на NAS, который нужно заменить | Путь в контейнере | Доступ контейнера |
| --- | --- | --- | --- |
| Очередь, токены и настройки | `/mnt/CHANGE_ME/appdata/mail_cloud` | `/state` | Чтение и запись |
| Фотографии | `/mnt/CHANGE_ME/photos` | `/photos` | Только чтение |

Для состояния создайте отдельный **локальный ZFS dataset**. SQLite использует файлы блокировки и журнал рядом с базой: не размещайте работающую очередь на сетевом SMB/NFS mount или в OneDrive и других синхронизируемых каталогах. Не давайте общему SMB-ресурсу доступ к токенам состояния.

Фотографии могут находиться в существующем dataset, который также используется другими программами. Подключайте только нужный каталог. Не монтируйте весь pool, `/mnt` или корень NAS: все подключённые пути под `/photos` становятся доступны пользователю панели.

В YAML указано `create_host_path: false`: опечатка в пути вызовет ошибку запуска, а не создаст пустую папку. Каталоги надо подготовить заранее. Это поведение описано в [Docker Compose: bind mounts](https://docs.docker.com/reference/compose-file/services/#volumes).

## 2. Настроить UID/GID и права

Образ запускается как **`1000:1000`**. В YAML эта пара задана явно. Это UID/GID процесса внутри контейнера, а не утверждение о пользователях вашего NAS.

Выбранной паре UID/GID нужны:

- чтение, создание и изменение файлов в dataset состояния;
- чтение фотографий и проход по всем родительским каталогам источника;
- доступ через действующие ACL, если dataset использует ACL.

Подстройте владельца или ACL **выделенного dataset состояния** и права чтения фотокаталога под выбранного пользователя. Не применяйте рекурсивную смену владельца ко всему фотоархиву или pool.

Если вы осознанно используете пользователя TrueNAS `apps` с UID/GID `568:568`, поменяйте строку на `user: "568:568"` и выдайте соответствующие права. Значение `568` не является обязательным для этого образа. Существующие файлы состояния также должны принадлежать доступному контейнеру пользователю; `auth.dat` и `web_access.json` должны оставаться приватными файлами с правами `600`.

`PUID` и `PGID` из `.env.example` используются обычным Compose-файлом для поля `user`. В TrueNAS YAML указывается непосредственно `user`; дополнительные переменные `PUID`/`PGID` образу не нужны.

## 3. Установить приложение

Образ `ghcr.io/zhalenik/mail_cloud:stable` доступен без учётных данных registry. Токен GitHub для установки не нужен. Версии и изменения перечислены в [выпусках проекта](https://github.com/zhalenik/mail_cloud/releases).

1. Откройте [готовый deploy/truenas-compose.yaml](../deploy/truenas-compose.yaml).
2. Замените оба `source: /mnt/CHANGE_ME/...` на существующие пути NAS.
3. Проверьте `user: "1000:1000"` по выбранным правам.
4. В `MAILRU_ALLOWED_HOSTS` укажите IP или DNS-имя, которым будете открывать панель. В примере это `192.168.1.10`.
5. Откройте **Apps → Discover Apps → ⋮ → Install via YAML**.
6. Укажите имя приложения `mail-cloud`, вставьте весь YAML в **Custom Config** и сохраните.
7. Дождитесь состояния Running и откройте [http://192.168.1.10:31800](http://192.168.1.10:31800).

В этом файле нет обязательного `.env` и скрытых подстановок `${...}`: все необходимые параметры видны в YAML. Инструкция по этому экрану есть у [TrueNAS: Installing Custom Apps](https://apps.truenas.com/managing-apps/installing-custom-apps/).

### Кнопка Web UI, версия и значок

В шаблон добавлено расширение Compose `x-portals`:

```yaml
x-portals:
  - name: Web UI
    scheme: http
    host: "0.0.0.0"
    port: 31800
    path: /
```

В исходниках **24.10.2.3** оно обрабатывается при создании custom app, а `0.0.0.0` в адресе портала заменяется адресом NAS. Это метаданные ссылки; они не меняют публикацию `31800:8787` и не означают привязку сервиса к новому IP. [Разбор порталов](https://github.com/truenas/middleware/blob/TS-24.10.2.3/src/middlewared/middlewared/plugins/apps/ix_apps/portals.py), [обновление метаданных](https://github.com/truenas/middleware/blob/TS-24.10.2.3/src/middlewared/middlewared/plugins/apps/ix_apps/metadata.py).

Есть ограничение: ветка редактирования уже установленного **YAML custom app** в этой версии не обновляет порталы тем же способом. Поэтому добавление блока в существующий YAML может не создать кнопку. Общая документация TrueNAS описывает отсутствие Web UI у YAML-приложений; проверка расширения выше основана на исходниках точного выпуска, а не на проверке вашего NAS. Если кнопка не появилась, используйте сохранённый адрес `http://<адрес-NAS>:31800`. Поддерживаемая настройка через форму **Custom App → Portal Configuration** описана в [справке 24.10](https://www.truenas.com/docs/scale/24.10/scaleuireference/apps/installcustomappscreens/); [ограничения управления YAML-приложениями](https://apps.truenas.com/managing-apps/managing-installed-apps/#managing-custom-apps).

Поля **App Version: custom**, **Version: 1.0.0**, стандартный значок и **Source: N/A** относятся к оболочке Custom App в TrueNAS. Они не показывают версию контейнера. Эта оболочка задаёт свои значения независимо от OCI-меток образа: [модель Custom App для этой версии](https://github.com/truenas/apps_validation/blob/766d75c01a68c84f7d800908b550f737ec08cb83/catalog_reader/custom_app.py). Произвольные `labels` в Compose не превратят её в приложение каталога с собственной историей версий и логотипом. Рабочую версию клиента смотрите внизу его панели либо в стартовой строке журнала `Mailru Photo Client …`. Не редактируйте служебные файлы `.ix-apps` для подмены карточки.

### Как связаны порт и разрешённый адрес

```yaml
ports:
  - "31800:8787"
environment:
  MAILRU_ALLOWED_HOSTS: "192.168.1.10"
```

Публикация порта Docker и проверка `Host` приложением выполняют разные задачи:

| Параметр | Что он делает |
| --- | --- |
| `31800:8787` | Направляет обращения к порту `31800` NAS на порт `8787` контейнера; отдельный IP в этой записи не требуется. |
| `MAILRU_ALLOWED_HOSTS` | Разрешает конкретные имена/IP в HTTP-заголовке `Host`, защищая панель от чужих имён и DNS rebinding. Не управляет сетевым bind Docker. |
| `MAILRU_PUBLIC_ORIGIN` | Задаёт полный внешний origin за reverse proxy; при прямом LAN-доступе оставляется незаданным. |

Для доступа и по IP, и по локальному DNS-имени можно написать `MAILRU_ALLOWED_HOSTS: "192.168.1.10,nas.example.lan"`. Используйте имена без схемы и порта. Маска `*` не поддерживается.

Без `MAILRU_PUBLIC_ORIGIN` приложение само учитывает текущий `Host`, включая `:31800`, при проверке origin. Менять код или отключать эту проверку для доступа по LAN не нужно.

## 4. Выполнить первый запуск в браузере

1. Задайте отдельный пароль панели длиной не менее 12 символов.
2. Подключите аккаунт Mail, введя адрес и пароль внешнего приложения.
3. В разделе «Исходные папки» выберите `/photos` или нужную подпапку, имя источника и полный путь в Облаке, например `/PhotoArchive/Family`. Для каждого источника назначение независимо.
4. Нажмите **«Начать загрузку»**. Клиент выполнит нужное сканирование и начнёт обработку очереди.

Фото и видео передаются с NAS напрямую в Облако. Браузер отображает состояние; закрытие вкладки не останавливает контейнер. Кнопка **«Приостановить»** сохраняет очередь и отменяет намерение автоматически продолжить текущую загрузку. Если автопродолжение включено и загрузка была активна до штатного перезапуска контейнера, приложение попробует продолжить её.

Контрольного файла и ожидания квоты перед основной загрузкой нет. После сканирования панель показывает объёмы задач и предупреждает о расходовании места. Политику обычной загрузки и действий при неожиданном результате можно выбрать в настройках; [подробнее](WEB_GUI_RU.md#политика-хранения). Подтверждение режима хранения, размер и хеш проверяются для каждого загруженного файла.

## Несколько папок с фотографиями

Если нужные папки уже находятся внутри одного подключённого каталога, добавьте каждую из них через панель. Для отдельных dataset замените один photo mount несколькими. Mount `/state` сохраните:

```yaml
volumes:
  - type: bind
    source: /mnt/CHANGE_ME/appdata/mail_cloud
    target: /state
    bind:
      create_host_path: false
  - type: bind
    source: /mnt/CHANGE_ME/family_photos
    target: /photos/family
    read_only: true
    bind:
      create_host_path: false
  - type: bind
    source: /mnt/CHANGE_ME/archive_photos
    target: /photos/archive
    read_only: true
    bind:
      create_host_path: false
```

В панели добавьте `/photos/family` и `/photos/archive` с разными именами источников. Образ уже разрешает корень `/photos`; менять команду запуска для его подпапок не нужно. Не добавляйте одновременно `/photos` целиком и его дочерние папки как перекрывающиеся источники.

## Удаление исходников с диска

Обычная установка подключает фотоархив только для чтения. Загрузке и просмотру этого достаточно. Если требуется удалять оригиналы через панель, при остановленном приложении измените **у соответствующего photo mount**:

```yaml
volumes:
  - type: bind
    source: /mnt/CHANGE_ME/photos
    target: /photos
    read_only: false
    bind:
      create_host_path: false
```

Сохраните остальные mount, включая `/state`. Выбранному UID/GID нужны права удаления в каталоге и соответствующие разрешения ACL. `read_only: true` на уровне всего сервиса можно оставить: он защищает корневую файловую систему контейнера, а не явно подключённый writable dataset.

В диалоге удаления исходник выбирается отдельной галочкой, после чего нужно ввести `УДАЛИТЬ С ДИСКА`. Удаление с диска безвозвратно. Файл в Облаке по отдельному выбору отправляется в корзину. Ввод фразы не обходит read-only mount или ACL: при отказе задача показывает причину.

## Планировщик

В меню **«Планировщик»** добавьте расписание, выберите одну или несколько исходных папок, время и дни недели либо числа месяца от 1 до 30. Все дни недели выбраны по умолчанию. Каждое расписание включается отдельно; редактирование или удаление не требует пересоздания приложения.

Время задаётся в часовом поясе панели. Начальное значение — `Europe/Moscow`, его можно изменить в настройках на другой пояс IANA. В контейнер включены данные `tzdata`; при первой установке можно задать `MAILRU_TIMEZONE`, но уже сохранённая настройка панели имеет приоритет. Часовой пояс браузера не меняет расписания.

В заданное время клиент сканирует только выбранные источники, дожидается завершения обхода и выполняет их готовые задачи. Если клиент занят, сработавшее расписание сохраняется в очереди запусков. Пропущенные моменты во время выключенного сервера не выполняются задним числом; уже сохранённые срабатывания переживают перезапуск. Общая пауза отменяет уже ожидающие срабатывания, но будущие расписания остаются включёнными. На странице видны ближайший запуск и результат предыдущего. [Полные правила](WEB_GUI_RU.md#планировщик).

## Обновление

| Значение `image` | Как выбирать обновления |
| --- | --- |
| `ghcr.io/zhalenik/mail_cloud:stable` | Получать новые выпуски без изменения тега в YAML. |
| `ghcr.io/zhalenik/mail_cloud:v0.8.0` | Использовать выбранный выпуск. Для следующей версии изменить тег в YAML. |
| `ghcr.io/zhalenik/mail_cloud@sha256:…` | Закрепить конкретный digest опубликованного образа, если нужна точная фиксация содержимого. |

Версионный тег удобен для выбора выпуска; технически владелец registry может перезаписать любой тег. Digest фиксирует конкретное содержимое; см. [Docker: получение образа по digest](https://docs.docker.com/reference/cli/docker/image/pull/#pull-an-image-by-digest-immutable-identifier). Наличие новой версии приложения в GitHub само по себе не меняет YAML с фиксированным тегом.

### Одна настройка для канала stable

В существующем YAML у сервиса должны быть обе строки:

```yaml
services:
  mailru-photos:
    image: ghcr.io/zhalenik/mail_cloud:stable
    pull_policy: always
```

Добавьте `pull_policy` через **Apps → mail-cloud → Edit**; остальные параметры вашего YAML сохраните. Новый шаблон уже содержит эту настройку. Обновление файла в GitHub или самого образа не меняет YAML ранее установленного приложения — один раз поправить его нужно на NAS.

Без `pull_policy` Compose использует политику `missing`: существующий локальный образ с тегом `stable` можно получить снова даже после переустановки приложения. `always` заставляет Compose проверять образ в registry при развёртывании. Неизменившиеся слои повторно не скачиваются. [Описание Docker Compose](https://docs.docker.com/reference/compose-file/services/#pull_policy).

### Как установить следующий выпуск

1. Приостановите загрузку в панели и дождитесь её остановки.
2. Остановите приложение в TrueNAS и сделайте ZFS snapshot dataset состояния.
3. Нажмите **Start**. С `stable` и `pull_policy: always` TrueNAS получит текущий образ и создаст контейнер с ним. Номер версии менять не требуется.
4. Проверьте версию в панели, очередь и настройки, затем продолжите загрузку.

Сохраняйте тот же mount `/state`, пути источников внутри `/photos` и согласованный UID/GID. Для запуска с `pull_policy: always` серверу нужен доступ к GHCR. Настройка `restart: unless-stopped` сама по себе образы не обновляет: перезапуск процесса Docker после сбоя или загрузки NAS отличается от **Start** приложения в TrueNAS.

### Почему может не быть кнопки Update

TrueNAS проверяет обновления образов отдельно от `pull_policy`. В **Apps → Configuration → Settings** должен быть включён **Check for docker image updates**. В исходниках **24.10.2.3** фоновая проверка назначена раз в **24 часа** и запускается также при старте Docker-сервиса. Это не означает немедленную проверку после каждого перезапуска приложения. [Настройка в документации](https://www.truenas.com/docs/scale/24.10/scaleuireference/printpreview/) и [планировщик проверки в исходниках](https://github.com/truenas/middleware/blob/TS-24.10.2.3/src/middlewared/middlewared/plugins/docker/state_management.py).

Проверяется digest **того же тега**, который указан у работающего контейнера. Для `stable` он меняется при выпуске новой версии. Для закреплённого `v0.4.4` или `v0.8.0` наличие следующего тега не является обновлением выбранного образа. Ошибки доступа к registry записываются в журналы и могут оставить прежний результат проверки; `Up to date` не подтверждает успешное получение свежего списка прямо сейчас. [Сравнение образов в 24.10.2.3](https://github.com/truenas/middleware/blob/TS-24.10.2.3/src/middlewared/middlewared/plugins/apps_images/update_alerts.py).

`pull_policy: always` проверяет образ при развёртывании через Compose; он не включает этот фоновый индикатор. Для обновления без ожидания используйте описанный выше **Stop → Start** с `stable` и `always`, предварительно остановив загрузку и сохранив снимок состояния. Другой доступный путь — **Apps → Configuration → Manage Container Images → Pull Image**, затем развёртывание приложения. [Экран управления образами](https://www.truenas.com/docs/scale/24.10/scaleuireference/apps/#manage-container-images).

На SCALE 24.10 обновление через **⋮ → Update** требует запущенного приложения. При использовании этой кнопки приостановите работу внутри клиента; после создания снимка запустите приложение и выберите Update, если оно доступно. [Официальный порядок](https://apps.truenas.com/managing-apps/managing-installed-apps/#updating-apps).

### Закрепление версии и откат

Для конкретной версии измените строку `image`, например:

```yaml
image: ghcr.io/zhalenik/mail_cloud:v0.4.4
pull_policy: always
```

При проверке перед выпуском 0.7.0 публичный тег `v0.4.4` по-прежнему содержал именно версию 0.4.4; он не был перезаписан содержимым 0.6.0. Штатное сохранение YAML в изученных исходниках 24.10.2.3 не переписывает `stable` в номер выпуска и не подменяет указанный `v0.4.4` на более поздний тег. Наблюдаемое на конкретном NAS переключение без его фактической конфигурации и журнала не воспроизведено. [Сохранение Custom App](https://github.com/truenas/middleware/blob/TS-24.10.2.3/src/middlewared/middlewared/plugins/apps/crud.py).

Если после изменения запускается не тот выпуск, проверьте сохранённое поле `image` в **Edit**, образ работающего контейнера в **Workloads** и версию внутри клиентской панели/стартового журнала. Поля `custom`/`1.0.0` карточки приложения для такой проверки не подходят. `pull_policy: always` не может обновить уже работающий процесс без нового развёртывания.

**Откат образа и откат базы — две отдельные операции.** В 0.4.4 схема базы 1, в 0.5.0 — 2, в 0.5.1–0.6.0 — 3, в 0.7.0 — 4, в 0.8.0 — 5. Новая версия мигрирует старое состояние автоматически. Старая версия должна отказать в открытии более новой схемы; такой отказ не означает, что TrueNAS выбрал другой образ.

Для возврата остановите приложение, сохраните текущее состояние отдельно, восстановите snapshot всего dataset `/state`, сделанный до нужного обновления, и укажите соответствующий старый образ. Затем проверьте путь mount и версию в панели. Встроенный Roll Back оболочки Custom App не является историей тегов нашего контейнера и не заменяет восстановление bind-mounted dataset.

Восстановление старого состояния не отменяет уже выполненные операции в Облаке. Сохраните исходные фотографии и современный snapshot, пока не убедитесь, что выбранная комбинация образа и состояния работает. Для обычного обновления сохраняйте `/state`, внутренние пути `/photos/...` и UID/GID. Приложению отведено `120s` на штатную остановку.

### Автоматическая копия очереди перед миграцией

Перед переходом со старой схемы на 5 создаётся самостоятельный файл вида `/state/backups/queue-schema4-before5-YYYYmmddTHHMMSSZ-xxxxxxxx.sqlite3`. Число после `schema` — исходная схема: оно может быть 1, 2, 3 или 4. Копия включает зафиксированные данные WAL, сохраняет исходный `user_version`, задачи и подтверждения операций; отдельные WAL/SHM для неё не нужны. При невозможности создать копию миграция не продолжается.

В эту копию **не входят** `auth.dat`, настройки панели, проект и база планировщика. Основной способ отката — snapshot всего dataset состояния. Если используется только автоматическая копия очереди, остановите все процессы клиента, сохраните текущие `queue.sqlite3`, `queue.sqlite3-wal` и `queue.sqlite3-shm` отдельно, затем верните выбранную копию как `queue.sqlite3` без чужих sidecar-файлов и запустите совместимый старый образ. Копия схемы 3 подходит для 0.6.0, но не превращается в схему 1 для 0.4.4.

## Перенос существующего состояния

Состояние включает не только `queue.sqlite3`, но и авторизацию, настройки и служебные файлы. Сохраняйте всю папку после остановки использующего её процесса. Одновременно открывать одно состояние из двух экземпляров приложения нельзя.

**Автоматическая миграция Windows-очереди на TrueNAS пока не реализована.** Очередь хранит абсолютные пути источников, а токены Windows могут быть защищены DPAPI. Копирование папки состояния в Linux само по себе не преобразует ни пути, ни токены.

Сохраните исходную Windows-папку состояния и исходные фотографии. Не редактируйте пути в SQLite вручную и не заменяйте работающую очередь новой. Для независимой установки на NAS используйте отдельный dataset состояния и отдельную папку назначения в Облаке, пока перенос с сохранением истории не реализован и не проверен.

При переносе существующей Linux-установки также нужно сохранить пути, которые видит приложение. Замена пути на NAS при неизменном `/photos/...` внутри контейнера отличается от изменения самого `/photos/...` в уже созданной очереди.

## Если приложение не запускается

| Симптом | Что проверить |
| --- | --- |
| Образ не найден, `manifest unknown` | Завершилась ли первая публикация GHCR; существует ли выбранный тег. |
| `denied` при получении образа | Доступность пакета GHCR. Публичность GitHub-репозитория сама по себе не гарантирует публичность пакета; см. [настройки доступа GitHub Packages](https://docs.github.com/en/packages/learn-github-packages/about-permissions-for-github-packages). |
| Ошибка bind mount | Существуют ли оба `source` и заменены ли все `CHANGE_ME`. |
| `Permission denied` или панель не создаёт состояние | UID/GID, владелец, ACL, проход по родительским каталогам и доступ на запись в `/state`. |
| `403`, имя сервера не разрешено | Совпадает ли адрес в браузере с `MAILRU_ALLOWED_HOSTS`; указано ли имя без схемы и порта. |
| `403`, запрос должен исходить из этой панели | Не задан ли лишний `MAILRU_PUBLIC_ORIGIN`; совпадают ли схема, имя и порт с фактическим адресом панели. |
| В браузере нет соединения | Состояние приложения, занятость порта `31800`, маршрут и правила вашей сети. |
| В панели не видны папки | Mount фотографии, права чтения/прохода и пути внутри `/photos`. |
| Очередь занята | Не работает ли другой CLI или контейнер с тем же состоянием. |

Начните с журналов приложения в интерфейсе TrueNAS. В журнал выводятся фазы работы и счётчики прогресса, а подробные ошибки доступны в панели. Для обращения в Issues достаточно версии и обезличенного текста ошибки; не прикладывайте dataset состояния, токены или полный фотоархив.
